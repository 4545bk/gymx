3. QR check-in data flow
This is the most latency-sensitive path in the entire system. Every decision here is made to hit that sub-1-second target.



The key architectural decision here is the Redis cache. When the scanner hits the API, you look up the member in Redis first — this is an in-memory operation that takes under 5ms. MongoDB is only touched on a cache miss. The TTL on each Redis record should be 24 hours, refreshed whenever a member's data changes. This means at peak morning rush (50 people scanning in 10 minutes), MongoDB sees almost zero load from check-ins.

The scanner authenticates using a static API key (a long random string stored in the environment). No JWT, no login — it's a machine credential. The API key is validated as the very first middleware so invalid requests are rejected at the edge before any database work happens.

4. Scalability considerations
At 5,000 members with realistic gym usage patterns (perhaps 300–500 check-ins on a busy day), MongoDB with proper indexing is completely sufficient. The critical indexes are:

members collection: index on memberId (the QR token — this is the hot path), index on phone and name for receptionist search
attendance collection: compound index on { memberId, date } — both for duplicate-check queries and for reporting
payments collection: index on { memberId, date }
No sharding, no replica sets needed at launch. If you ever hit 50,000+ members, adding a MongoDB replica set is a single config change. The Redis cache is the real scalability lever — it decouples your busiest operation (check-in) from your database entirely.

On the API side, Node.js with Express is single-process by default. Use the Node.js cluster module or PM2 in cluster mode to spawn one worker per CPU core. This gives you horizontal scaling on a single server with zero infrastructure changes.

5. Security considerations
Three layers of security matter here:

Authentication uses JWT with short-lived access tokens (15 minutes) and refresh tokens (7 days) stored in HTTP-only cookies. Never store JWTs in localStorage. Each token payload carries { userId, role } — the role guard middleware checks this on every protected route before the request reaches the controller.

Role permissions should be enforced at the API level, not just the frontend. The frontend hiding a button is UX — the API refusing the request is security. A receptionist token must be rejected by the API if it tries to access owner-only endpoints like financial reports or staff salary data.

The QR code itself should encode a unique memberId (a UUID, not the MongoDB _id) that is stable across the member's lifetime. Never encode anything sensitive in the QR. The value is meaningless to an attacker because the API key that the scanner uses to call the check-in endpoint is the actual credential — the memberId alone does nothing.

Input validation with a library like Zod on every request body. MongoDB injection is a real concern — never pass raw user input into a query without schema validation first.

This is the most latency-critical piece of the entire system, so every decision here needs justification. Let me walk through each layer in depth.

How the scanner works — the hardware reality
A USB QR scanner acts as a keyboard. When a member holds their QR code up to it, the scanner "types" the encoded string into whatever input has focus — exactly as if someone typed it at speed. This means your check-in station needs a dedicated browser page with an invisible input field that auto-captures every keystroke and submits when it detects a full token (either a fixed length or a terminating character like Enter). There is no "scan event" — just keyboard input that your frontend catches and fires at the API.

This matters for architecture because the entire check-in flow is initiated from a single, always-on browser tab, not from the main dashboard.



Step-by-step backend logic
Step 1 — Frontend capture
The check-in station runs a dedicated page at /checkin. On load, it focuses an invisible <input> field and listens for keydown events. Every character the scanner types accumulates in a buffer. When the scanner sends an Enter keypress (which all hardware scanners do by default after the barcode), the frontend fires the API call and clears the buffer. A 500ms debounce prevents double-fires if the scanner misfires.

The frontend also handles the display — a large green/red feedback panel showing the member's name, plan, and result. This is separate from validation: the frontend does no validation itself, it only shows what the API returns.

Step 2 — API key authentication
The scanner station is configured (once, at setup) with a static API key stored in its environment. Every request from the scanner includes this in the x-scanner-key header. Middleware checks it with a constant-time string comparison (using crypto.timingSafeEqual) to prevent timing attacks, and rejects anything that doesn't match before any other code runs. This is intentionally not a JWT — the scanner never "logs in." It has one permanent credential.

Step 3 — Input parsing and format validation
The body contains { memberId: "MBR-7F3A9C2B" }. Before any database work, validate the format with a strict regex: /^MBR-[A-Z0-9]{8}$/. This catches corrupted scans, partial reads, or garbage input in under 1ms. Return 400 immediately if it fails — no Redis, no MongoDB touched.

Step 4 — Redis lookup
GET member:MBR-7F3A9C2B
The cached value is a JSON string containing exactly what the check-in logic needs: status, plan.type, plan.allowedDays, plan.expiryDate, fullName, and assignedTrainerId. Nothing else. The cache was populated either when the member was registered, or on the last cache miss.

TTL on every key is 24 hours. When a receptionist updates a member's plan or status, the service layer must immediately invalidate that Redis key (DEL member:{memberId}). This is the only cache invalidation event — every write to a member document triggers a Redis delete, forcing a fresh DB read on the next scan.

On a cache miss, query MongoDB using the memberId index (not _id), populate the cache, then continue. Even on a miss, the MongoDB query on an indexed field over 5,000 documents takes under 5ms.

Step 5 — Membership status check
if (member.status !== 'active') → deny
The status field is an enum. Any value other than "active" — whether "expired", "suspended", or "frozen" — is a hard deny. Return a specific reason code so the frontend can show the right message. Do not conflate "suspended" with "expired" — the receptionist needs to know which one it is.

Step 6 — Expiry date check
Timezone is critical here. All dates in MongoDB are stored as UTC. Ethiopia is UTC+3. A membership that expires on May 31 should be valid all day May 31 Addis Ababa time, which runs from May 31 00:00 to May 31 20:59 UTC. The comparison must be done against the member's local date, not UTC date, or members will be wrongly denied for the last 3 hours of their last valid day.

todayLocal = currentDateInUTC+3()
if (member.plan.expiryDate < todayLocal) → deny, reason: "expired"
Additionally, if a member is denied because they're expired, immediately mark their status as "expired" in MongoDB and invalidate their Redis cache. This prevents their status from showing as "active" in the dashboard while the scanner correctly denies them.

Step 7 — Allowed days check
if (member.plan.type === '3-day') {
  todayWeekday = getDayOfWeek()  // 1=Mon … 7=Sun
  if (!member.plan.allowedDays.includes(todayWeekday)) → deny, reason: "wrong-day"
}
// full-week members: skip this check entirely
The response for a wrong-day denial should include the next allowed day so the front panel can display "Next allowed day: Wednesday." This costs nothing to compute and saves confusion.

Step 8 — Duplicate scan prevention
This is the step that touches the database, but it does so through the unique compound index rather than a query-then-write pattern.

The approach is optimistic insert, not check-then-insert:

Instead of first querying attendance to see if a record exists, directly attempt the insert. If the document inserts successfully, the scan is the first of the day — grant entry. If MongoDB throws a duplicate key error (error code 11000) on the { memberId, date } unique index, the member already checked in today — deny with reason "duplicate". This is faster than check-then-insert because it's one database round trip instead of two, and it's race-condition safe because the uniqueness is enforced at the index level, not in application code.

try {
  insertOne({ memberId, date: todayLocal, status: "granted", ... })
  → grant entry
} catch DuplicateKeyError {
  → deny, reason: "duplicate"
}

  status: "granted",
  denyReason: null,
  planSnapshot: { type: "3-day", expiryDate: ISODate("2026-06-01") }
}
The planSnapshot is embedded, not referenced, so the attendance log is a faithful historical record regardless of future plan changes.

Denied scans are also written, but as status: "denied" with a denyReason. This gives you a complete audit trail — you can see every denied entry attempt, which is useful for identifying members who repeatedly scan on wrong days or who are unaware their membership lapsed.

Step 10 — Post-grant expiry warning
After writing the attendance record (not before — don't delay the response for this), check if expiryDate - today <= 5 days. If so, queue an alert insert into the alerts collection. This write is done asynchronously — the API response is sent immediately after the attendance write, and the alert insert happens in a setImmediate callback. The member gets their grant in under 200ms; the alert appears in the receptionist's panel within seconds.

Performance optimization techniques
The 200ms target breakdown:

Stage	Target latency
Network (scanner → server, LAN)	< 5ms
API key check	< 1ms
Format validation	< 1ms
Redis lookup (cache hit)	< 3ms
Validation logic (in-memory)	< 1ms
MongoDB attendance write	< 10ms
Response serialization	< 1ms
Total	< 22ms (leaves 978ms of buffer)
1. Keep the Redis payload tiny. Only cache the fields the check-in logic actually needs. Don't cache the whole member document including photoUrl, emergencyContact, and registeredBy. A 200-byte Redis value is faster to deserialize than a 2KB one.

2. MongoDB write concern: { w: 1 } — the default, acknowledge from the primary only. Don't use { w: "majority" } on the check-in write path. The attendance write is not so critical that you need quorum acknowledgment — if a replica lags, the loss of a single attendance record is acceptable. Speed wins here.

3. Connection pooling. Mongoose maintains a connection pool. Set minPoolSize: 5 so connections are warm at startup and the first scan of the day doesn't pay a connection setup cost.

4. No middleware overhead on the check-in route. The check-in endpoint should not go through JWT auth middleware, session middleware, or rate limiting middleware. It has one job: check the scanner API key. All other middleware is wasted CPU cycles on the hot path.

5. The check-in page is a separate Next.js route with no layout, no navigation, no sidebar. It's a blank page with one invisible input, one feedback panel, and a WebSocket connection to the server for the live log. No heavy React component trees, no data fetching on render.

6. Graceful Redis fallback. If Redis is unavailable (restart, crash), the system must not go down. Wrap every Redis call in a try/catch. On failure, fall through to MongoDB. Log the Redis error, but serve the check-in. A slower check-in is better than no check-in.

7. Pre-warm the cache at start of day. Run a background job at 4:00 AM every day (before the gym opens) that fetches all active members and loads them into Redis. This eliminates cold-start cache misses for the first wave of morning check-ins. The job runs findAll({ status: 'active' }) and does a pipeline of Redis SET commands in a single batch.

8. Optimistic insert over check-then-write. Covered in Step 8 above. One round trip vs two, and race-condition proof at the DB level.

The check-in station setup
The check-in page should display a live feed of the last 10 check-ins, updated via a Server-Sent Events (SSE) stream. Every time an attendance document is written, the server pushes an event to the check-in page. The receptionist at the front desk can see who's coming in without running a query. This costs one SSE connection per check-in station — essentially free in terms of server resources.

The physical screen at the door shows only two things: the feedback panel (green/red/yellow with the member's name) and the live feed. No login prompt, no navigation. The page auto-reconnects the SSE stream if it drops, and refocuses the hidden input if the window loses focus.

API conventions
Before the endpoints, these global rules apply everywhere in the API.

All endpoints are prefixed with /api/v1. Versioning from day one costs nothing and saves a painful migration later. Base URL: https://yourdomain.com/api/v1.

All request and response bodies are JSON. Dates are ISO 8601 strings. All monetary amounts are integers in the smallest currency unit (Ethiopian cents, so 800 ETB = 80000).

Every response — success or failure — follows a consistent envelope:

js
// Success
{
  "success": true,
  "data": { ... }
}

// Paginated list
{
  "success": true,
  "data": [ ... ],
  "pagination": {
    "total": 342,
    "page": 1,
    "limit": 20,
    "totalPages": 18
  }
}

// Error
{
  "success": false,
  "error": {
    "code": "MEMBERSHIP_EXPIRED",
    "message": "This membership expired on 2026-04-30"
  }
}
Using machine-readable error.code strings (not just HTTP status codes) means the frontend can make decisions — show the right panel, display the right message — without parsing human-readable strings.

Authentication design
The system uses two credential types that never mix.

Staff JWT flow: Staff log in with email + password. The server issues a short-lived access token (15 min) and a long-lived refresh token (7 days) stored in an HTTP-only cookie. The access token travels in the Authorization: Bearer <token> header on every request. The refresh token is never sent with API calls — only to the dedicated /auth/refresh endpoint. When the access token expires, the frontend silently calls /auth/refresh to get a new one. Staff never see this happen.

Scanner API key: A single static secret, configured once, sent in x-scanner-key header. No expiry, no refresh. Rotated manually if compromised.

Role hierarchy:

owner
  └── can do everything

receptionist
  └── check-in, member CRUD, payment recording, inventory view, alert read

trainer
  └── view their assigned members, view attendance of their members
The role is embedded in the JWT payload as { staffId, role }. Every protected route declares which roles may call it. Middleware enforces this before the controller runs.

Role-access summary


Key design decisions worth noting
The check-in endpoint returns HTTP 200 for both grants and denials. This is the right call because the request itself succeeded — a 4xx would cause frontend error handlers to fire, complicating the display logic. The result field in the response body carries the actual outcome.

Financial amounts are stored and returned as integers (Ethiopian cents) to avoid floating-point rounding issues entirely. The frontend divides by 100 for display. This is the same convention used by Stripe and every serious payment system.

Payment deletion is a void, not a delete. The database row is never removed. An owner can mark a payment as voided, but the audit trail is permanent. This is non-negotiable for any financial system.

The reports endpoints are kept separate from the data endpoints. They run aggregation pipelines against MongoDB and are expected to be slower — several hundred milliseconds is acceptable for a report, not for a check-in. Keeping them isolated means you can add caching or rate limiting to reports independently without touching the hot paths.

The trainer role's data access is enforced at the service layer, not just middleware. When a trainer calls GET /members, the service automatically appends { assignedTrainerId: req.staff.id } to the query — the trainer never sees this filter, and there's no way to bypass it by manipulating query params.
