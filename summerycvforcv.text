3. FULL PROFESSIONAL DESCRIPTION
================================================================================

GymX is an enterprise-grade gym management and operations platform purpose-built
for Ethiopian fitness businesses including Rose Fitness and BlackMagic Gym. The
system replaces manual spreadsheet-based workflows with a centralized digital
platform that handles the full member lifecycle — from registration and QR-based
check-in to financial tracking, point-of-sale transactions, and business
intelligence reporting.

The platform follows a decoupled client-server architecture with a Next.js 14
frontend (App Router, SSR + client components) communicating with a RESTful
Express 4.21 API layer backed by MongoDB Atlas for persistence and Redis for
high-throughput caching on the check-in hot path. The system implements 14
self-contained feature modules across 60+ API endpoints, enforced by a
role-based access control (RBAC) matrix spanning three permission tiers
(Owner, Receptionist, Trainer).

Key engineering highlights include a 12-step QR check-in pipeline achieving
<200ms latency on cache hits via a Redis cache-aside pattern with graceful
MongoDB fallback, an immutable append-only financial ledger inspired by
double-entry bookkeeping, atomic inventory operations using MongoDB $inc with
$gte guards to prevent overselling, Server-Sent Events (SSE) for real-time
check-in streaming, and automated background job scheduling via node-cron for
membership expiry detection, overdue billing, cache pre-warming, and equipment
maintenance alerts.

The platform is deployed on Render (backend) and Vercel (frontend) with
MongoDB Atlas as the managed database layer, serving Rose Fitness and
BlackMagic Gym in daily production use.

7. TECHNICAL CHALLENGES SOLVED
================================================================================

CHALLENGE 1: Sub-200ms QR Check-In Latency
  Problem: Hardware QR scanners require near-instant validation response to
  avoid queuing members at the gym entrance during peak hours.
  Solution: Implemented a Redis cache-aside pattern where active member data
  is pre-warmed daily and cached with 24-hour TTL. Cache hits resolve in ~1ms.
  Built graceful fallback to MongoDB for cache misses, and used optimistic
  attendance inserts with MongoDB duplicate key detection (error code 11000)
  to handle concurrent scans without distributed locks.

CHALLENGE 2: Financial Data Integrity
  Problem: Payment records must never be modified or deleted to maintain
  audit compliance and prevent financial discrepancies.
  Solution: Designed an immutable append-only ledger where payments are
  insert-only documents. Cancellations generate a separate reversal document
  referencing the original. All monetary values stored in cents (integer) to
  avoid floating-point rounding errors. Snapshot fields (memberName, planType)
  are denormalized at write time so financial records remain accurate even if
  the referenced member is later modified.

CHALLENGE 3: Race-Condition-Proof Inventory
  Problem: Concurrent POS transactions could oversell products if stock
  checks and decrements are not atomic.
  Solution: Used MongoDB's atomic $inc operator with a $gte guard in a single
  findOneAndUpdate call, ensuring stock can never go negative regardless of
  concurrency. Sale voids atomically restore stock using the same pattern.

CHALLENGE 4: Timezone-Aware Membership Expiry
  Problem: The system operates in Africa/Addis_Ababa (UTC+3) but servers may
  run in different timezones (Render's Frankfurt region).
  Solution: Used date-fns-tz for all date comparisons, stored timezone in
  environment configuration, and ran all background cron jobs with explicit
  timezone parameters. The 3-day plan day-of-week validation uses ISO weekday
  numbers to prevent locale-dependent day matching.

CHALLENGE 5: System Resilience
  Problem: Redis outages should not crash the check-in system or degrade the
  user experience.
  Solution: Implemented a graceful degradation layer where every Redis
  operation (get/set/del) is wrapped in safe functions that silently return
  null/false on failure. The system is fully functional without Redis — it
  simply falls back to MongoDB reads with slightly higher latency.

CHALLENGE 6: Secure Multi-Role Authentication
  Problem: Three user roles (Owner, Receptionist, Trainer) need different
  access levels across 60+ endpoints, plus hardware scanners need separate
  authentication.
  Solution: Implemented dual authentication: JWT-based auth for human users
  with 15-minute access tokens and 7-day HTTP-only refresh cookies, plus a
  separate API key authentication for QR scanner hardware. Built a composable
  roleGuard middleware that accepts allowed roles per route.

12. INTERVIEW EXPLANATION — "Tell me about your project"
================================================================================

"GymX is a full-stack gym management platform I built from scratch for two
Ethiopian fitness businesses — Rose Fitness and BlackMagic Gym. Before GymX,
they were tracking everything on paper and spreadsheets — member registrations,
payments, attendance — which was error-prone and time-consuming.

I designed the system as a decoupled architecture: a Next.js 14 frontend with
server-side rendering and client components, communicating with a RESTful
Express API backed by MongoDB Atlas and Redis.

The most interesting technical challenge was the QR check-in system. Gym
members scan a QR code at the entrance, and we need to validate their
membership in under 200 milliseconds — checking their status, plan expiry,
and even which days they're allowed (for 3-day plans). I solved this with a
Redis cache-aside pattern where active member data is pre-warmed daily.
Cache hits resolve in about 1 millisecond, and if Redis goes down, the system
gracefully falls back to MongoDB. I also used optimistic inserts with
MongoDB's duplicate key detection to handle concurrent scans without needing
distributed locks.

For the financial side, I designed an immutable ledger — payment records are
never updated or deleted. If you need to cancel a payment, the system creates
a separate reversal document. All amounts are stored in cents to avoid
floating-point issues, and I denormalize key fields like member name into the
payment record at write time so the financial history stays accurate even if
member data changes later.

The POS system was another challenge — I needed to prevent overselling when
multiple receptionists process sales simultaneously. I used MongoDB's atomic
$inc operator with a $gte guard, so stock decrements and floor checks happen
in a single atomic operation.

The system also runs four daily background jobs for cache pre-warming,
membership expiry detection, overdue billing, and equipment maintenance
alerts — all timezone-aware since the servers run in Frankfurt but the gyms
operate in Addis Ababa.

Security-wise, I implemented JWT authentication with 15-minute access tokens
and 7-day HTTP-only refresh cookies, plus a separate API key for the hardware
QR scanner. Every endpoint is gated by role-based access control with three
tiers — Owner, Receptionist, and Trainer.

Overall, the platform has 14 feature modules, over 60 API endpoints, and 12
database models. It's deployed on Render and Vercel and is being used in
production daily by Rose Fitness and BlackMagic Gym."
